# 轻橘 PopRoom — Stage 1 MVP 双机真机验收清单 (Expo Go)

> **适用版本**：Stage 1 MVP (`feat/stage1-mvp`)
> **测试环境**：2 台真机（建议 1 台 iOS + 1 台 Android，或 2 台同平台设备）安装 **Expo Go**，连接同一 Wi-Fi / Tunnel，对接已执行 `001`–`003` 迁移与 `room-media` 存储桶策略的 Supabase 实例。
> **设备角色约定**：
> - **Phone A（房主 Host）**：主测试账号 A
> - **Phone B（伙伴 Member）**：协同测试账号 B

---

## 0. 验前准备（Pre-Flight Check）

- [ ] `.env` 已配置 `EXPO_PUBLIC_SUPABASE_URL` 与 `EXPO_PUBLIC_SUPABASE_ANON_KEY`。
- [ ] 本地单元测试与类型检查全绿：
  - `npx.cmd vitest run`（全部通过）
  - `npx.cmd tsc --noEmit`（0 错误）
- [ ] 启动开发服务器：`npx.cmd expo start`，Phone A 与 Phone B 分别扫码打开 Expo Go。

## 1. M1：账号、进房门禁与成员管理闭环

### 1.1 邮箱密码注册与个人资料引导 (Onboarding)
- [ ] **Phone A**：进入登录页，切换「注册新账号」，使用新邮箱 + 密码（≥ 6 位）注册；自动进入 `/onboarding` 引导页。
- [ ] **Phone A**：设置昵称（如「阿橘」）并选择主题头像色，保存后进入活动大厅 `/(tabs)`。
- [ ] **Phone B**：重复上述注册与 Onboarding 流程，设置昵称（如「小满」），进入活动大厅 `/(tabs)`。

### 1.2 模板建房与 6 位房间码进房（直进模式 `passcode`）
- [ ] **Phone A**：点击「新建活动房间」，选择 **「校园 / 社团活动」** 或 **「多人出游 / 野营」** 模板，输入标题与活动时间，门禁选择 **「凭码直进」**，创建房间。
- [ ] **验证预设积木**：进入房间看板后，自动包含对应模板的投票、任务、日程、费用积木。
- [ ] **Phone B**：在活动大厅点击「输入房间码加入」，输入 Phone A 房间的 6 位房间码（验证自动转大写及 `0/O/1/I` 规范提示）。
- [ ] **预期结果**：Phone B 直接进入房间看板，Phone A 的「协作中人数」实时变为 2 人。

### 1.3 审批进房模式（`approval`）与加房审批
- [ ] **Phone A**：进入右上角「房间设置」，将门禁切换为 **「凭码申请审批」** 并保存；或新建一个审批模式房间。
- [ ] **Phone B**：输入新房间码，弹出申请备注输入框，填写备注（如「我是小满，负责物资」）后提交申请。
- [ ] **预期结果**：Phone B 提示「已提交入房申请，等待房主或管理员审批」，未审批前无法读取房间积木。
- [ ] **Phone A**：进入「房间设置 → 待审批入房申请」，能看到 Phone B 的昵称与申请备注；点击「通过」。
- [ ] **预期结果**：Phone B 在大厅刷新或再次点击即可进入房间看板（若点「拒绝」，则 Phone B 无法入房）。

### 1.4 未登录状态下的深链（Deep Link）拦截与自动回跳
- [ ] **Phone B**：在「我的」页面退出登录，确认处于未登录状态（`/(auth)/login`）。
- [ ] **Phone B**：通过系统浏览器 / 备忘录点击邀请深链 `/room/join?code=<6位房间码>`（独立构建 `poproom://room/join?code=<6位房间码>` / Expo Go `exp://.../--/room/join?code=<6位房间码>`，或使用 `npx.cmd uri-scheme open "poproom://room/join?code=<CODE>"` 测试）。
- [ ] **预期结果**：
  1. App 捕获 `pendingRoomCode`，但先拦截跳转至登录页（若新号则先走 Onboarding）。
  2. Phone B 完成登录后，路由守卫自动跳转至 `/room/join?code=<CODE>` 并预填房间码，完成入房，且不会循环重复弹出。

### 1.5 重置房间码使旧码失效
- [ ] **Phone A**：进入「房间设置」，记录当前旧房间码 `OLD_CODE`，点击 **「重置房间码」** 并确认。
- [ ] **预期结果**：
  1. 房间设置页展示全新 6 位房间码 `NEW_CODE`。
  2. 已在房内的 Phone B 不受影响，仍可正常协作。
  3. 使用未在房内的新账号或退出测试输入 `OLD_CODE` / 访问旧深链，均被拒绝并提示「房间不存在或房间码已失效」；输入 `NEW_CODE` 可正常加入。

### 1.6 移出成员（踢人防回流）
- [ ] **Phone A**：进入「房间设置 → 房间成员」，点击 Phone B 右侧移出按钮并确认踢出。
- [ ] **预期结果**：
  1. Phone B 看板收到实时更新或刷新后立即显示无法访问 / 「你已被移出该房间，无法再次加入」。
  2. Phone B 尝试再次输入有效房间码加入同一房间，服务端明确拒绝（`USER_KICKED`）。
  3. Phone A 在「操作日志」中可看到 `移出成员` 审计记录。
  > *注：完成本项验证后，Phone A 可再新建一个房间并将 Phone B 拉入，继续 M2/M3 测试。*

## 2. M2：四大协同积木、实时同步、离线可读与防手滑撤销

### 2.1 并发投票与空闲时间热力图实时同步
- [ ] **Phone A**：在「时间投票（热力图）」积木中勾选若干日期×时段；同时在「方案投票」中投选方案 A。
- [ ] **Phone B**：几乎同时在热力图中勾选相同与不同时段，并在方案投票中投选方案 B。
- [ ] **预期结果**：
  1. 两台手机各自的投票均成功保留，互不覆盖（基于 `poll_votes` 行级联合唯一约束 + `toggle_poll_vote` 原子 RPC）。
  2. 双方界面通过 Realtime 自动刷新票数与热力图深浅色阶（0–4 档暖橘热力色），最高票格子出现高亮标记。

### 2.2 匿名投票隐私校验（Review Focus #3）
- [ ] **Phone A**：新增一个开启 **「匿名投票」** 的投票积木，Phone A 与 Phone B 各自投票。
- [ ] **预期结果**：
  1. 双方 UI 仅显示票数与百分比，**绝不展示任何投票人头像或昵称**，且带有「匿名」标识。
  2. 核对服务端响应 / Supabase RPC `get_room_poll_tallies` 返回载荷：匿名投票条目的 `voter_ids` 必须被数据库强制掩码为 `[]`（空数组）。

### 2.3 并发任务认领、3 图实拍上传与条目评论
- [ ] **Phone A & B**：对同一条待办任务同时点击认领（或分别认领不同任务），状态从「待认领」自动流转为「进行中」。
- [ ] **Phone B**：进入任务详情弹窗，上传实拍图（最多支持 3 张，尝试上传第 4 张时前端与服务端均拦截并提示 `最多只能上传 3 张图片`）。
- [ ] **Phone A**：打开同一任务，确认能通过 Private Storage Signed URL 正常加载实拍缩略图与大图预览。
- [ ] **Phone A & B**：在任务详情底部互发评论，双方实时或刷新后均可见评论时间与昵称头像；Phone B 将任务状态切换为「已完成」，看板进度统计更新。

### 2.4 日程关键词地图导航与飞行模式离线只读
- [ ] **Phone A**：在「日程轴」新增 2 个日程（时间故意倒序录入，如先录 `14:00` 再录 `09:30`），填写地点关键词（如「深圳梧桐山南门」）。
- [ ] **预期结果**：
  1. 日程轴自动按 `startTime` 升序排列（`09:30` 在 `14:00` 之前）。
  2. 点击地点导航按钮，成功拉起本机高德地图 / Apple Maps / Google Maps 并传入地点关键词（无安装第三方地图时兜底跳转网页/系统地图）。
- [ ] **飞行模式离线读取测试**：
  1. Phone B 在正常联网状态下浏览完房间内所有积木后，开启手机 **飞行模式**（断开 Wi-Fi 与蜂窝数据）。
  2. 完全杀掉 Expo Go 后重新打开（或切换页面后返回该房间）。
  3. **预期结果**：借助 AsyncStorage 持久化的 TanStack Query 缓存，Phone B 仍可顺畅浏览房间公告、投票、任务、日程与账单信息，不白屏、不闪退。
  4. 恢复网络后继续后续测试。

### 2.5 AA 分账最小化转账校验（Review Focus #2）
- [ ] **Phone A**：在「AA 分账」积木记一笔 `100.00` 元，付款人为 Phone A，分摊人为 `[Phone A, Phone B, 第3人或仅2人]`（建议 3 人均分 `100.00` 测试余数守恒，或 2 人各自记多笔交叉垫付）。
- [ ] **Phone B**：再记一笔 `40.00` 元，付款人为 Phone B，由两人均分。
- [ ] **预期结果**：
  1. 净额守恒（所有成员净余额之和严格等于 `0.00`）。
  2. 结算建议展示最少笔数转账方案（例如 `100` 元 A 垫付 2 人均分 + `40` 元 B 垫付 2 人均分 → 仅需 1 笔：`B → A ¥30.00`），金额精确到分。

### 2.6 软删除与房主一键恢复（防手滑撤销）
- [ ] **Phone B**（或 **Phone A**）：在任务或日程积木中删除一条自己创建的条目，确认条目从看板消失。
- [ ] **Phone A**：进入「房间设置 → 操作日志与防手滑撤销」，在列表中找到对应的「删除条目」日志，点击 **「恢复」** 并确认。
- [ ] **预期结果**：
  1. 日志条目状态变为「已恢复」，重复点击恢复不会产生脏数据（服务端校验 `LOG_ALREADY_RESTORED`）。
  2. 双方房间看板立即恢复该条目及其原始数据内容。

## 3. M3：房间归档、全员只读守卫与 PNG / PDF 复盘导出

### 3.1 归档瞬间实时切换只读模式
- [ ] **准备**：Phone B 停留在房间看板页面（`app/room/[id]/index.tsx`）。
- [ ] **Phone A**：进入「房间设置」，滑到底部点击 **「归档活动（归档后全员只读）」** 并确认归档。
- [ ] **预期结果（Phone B 实时响应）**：
  1. Phone B 看板无需手动刷新，通过 Realtime `rooms` 事件立即在顶部弹出 **「活动已归档 · 全员只读模式」** 提示横幅。
  2. Phone B 页面上的添加积木、投票点击、任务认领/状态切换、添加/编辑/删除条目、上传图片、发送评论等写操作按钮全部隐藏或禁用。
  3. 即使在归档前打开的弹窗中强行点击提交，Supabase RLS / RPC 也必须拒绝写入并返回 `ROOM_ARCHIVED` 中文错误提示。

### 3.2 归档后双端导出高清复盘长图（PNG）与 A4 PDF
- [ ] **Phone A（Host）** 与 **Phone B（Member）** 分别在已归档房间顶部点击右上角分享/复盘按钮，进入 `/room/[id]/export` 页面。
- [ ] **预览检查**：
  1. 确认暖橘色主题结案卡片完整展示：品牌头图、活动名称、状态徽章（`已归档`）、参与人数、公告、**投票结论**（含平票并列标记，且匿名投票不泄露投票人）、**分工完成度进度条与清单**、**最终日程轴**、**费用总览与 AA 最小化结算方案**。
- [ ] **导出高清长图（PNG）**：
  1. Phone A 与 Phone B 分别点击底部 **「导出高清长图」**。
  2. **预期结果**：`react-native-view-shot` 成功截取整张长图并拉起系统分享面板；保存到相册或发送后检查图片清晰、文字无截断、无黑底透明异常。
- [ ] **导出 A4 PDF**：
  1. Phone A 与 Phone B 分别点击底部 **「导出 PDF」**。
  2. **预期结果**：`expo-print` 生成 A4 排版 PDF 并拉起系统分享面板；用系统自带 PDF 阅读器打开检查，样式为暖橘色调、中文字符渲染正常、无 HTML 标签注入或乱码。
